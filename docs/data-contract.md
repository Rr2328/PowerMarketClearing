# 数据契约 V1.3

> 电力现货市场出清仿真平台 · 全组共同遵守的数据格式约定
>
> - 修订：V1.3 按「逐时段申报（长表）· 报量报价单模式 · 96 点原生粒度」全面改版（依据 2026-08-31 设计讨论定稿 D1–D6、2026-09-02 补充拍板 D7 与长表格式）。
> - V1.3 相对 V1.2 的核心变化见第八章版本记录；**旧窄表文件无需修改，DataReader 兼容导入自动展开**（见第一章 1.3）。

## 一、总则

1. **适用范围**：本契约定义平台**全部输入数据**的格式，A（数据）、B（算法）、C（界面）三方共同遵守；任何字段增删改须全组同意并在第八章版本记录中登记。
2. **两类数据（先分清这个，很多问题就不会混）**：
   | 类型         | 内容               | 特点                                        | 谁产生           |
   | ---------- | ---------------- | ------------------------------------------ | -------------- |
   | **段申报（长表）** | 发电申报表、购电申报表     | 以 `period(1–96)` 为行、申报段（出力+报价成对列）横向展开；同一主体 96 行，可**逐时段差异化**申报 | 用户在 P1 编辑     |
   | **时段曲线**    | 负荷曲线、新能源出力       | 96 点**预测输入**（物理场景），非申报、不参与报价              | 典型日预设 × 峰值 / 渗透率自动生成 |

   出清时，每个时段取申报长表的**第 t 周期行**与场景曲线，交叉一次。
3. **单位与数值口径（教学约定）**：
   | 量           | 单位       | 精度         |
   | ----------- | -------- | ---------- |
   | 电价          | 元/MWh    | 三位小数（如 150.000） |
   | 电力（功率）      | MW       | 一位小数       |

   申报量表示**该时段可用于出清的功率**；撮合按数值直接相加、**不乘时段时长**。负荷曲线与出力曲线按 MW 存，全程数值口径一致。
4. **兼容导入（旧窄表 → 长表自动展开）**，分三步：
   - **识别**：DataReader 读表头，**无 `period` 列** → 判定为旧窄表（V1.2 及以前格式：一行 = 主体×段，含电价与申报量）；
   - **展开**：先按机组把多条段行**合并成对列**（段1量/价、段2量/价…），再**复制 96 份**（period 1–96），每份量、价完全相同——即"每个时段申报完全一样"；旧文件的「机组类型」列忽略不校验；
   - **展开后不锁死**：96 行只是初始值，导入后任意时段仍可单独编辑。

   > **为什么值得留**：旧引擎 `clearPeriods` 本来就是"每个时段塞同一组数据"跑 96 遍；展开后的长表喂给新引擎，逐时段出清结果应与旧引擎**完全一致**——这就是新旧对拍的锚点。因此基准例文件**不改格式**，窄表原样存档、导入即展开。
5. **双侧申报校验六规则**——数据保存/导入时逐条检查，**任一条不通过即拒绝保存**，并逐条给出可读的错误提示（提示信息按「发电 · / 购电 ·」分侧标注）：
   | #  | 规则                                                                    | 说明                                             |
   | -- | --------------------------------------------------------------------- | ---------------------------------------------- |
   | ①  | 每台机组 / 购电申报的申报段数 **≤ 5 段**                                              | 双侧对称简化（参照省间现货规则 4.2.3 条发电侧口径）                  |
   | ②  | 申报电价单调：对每一行（每个 period），**发电侧从低段到高段单调不减**；**购电侧从低段到高段单调不增**            | 双侧对称简化                                          |
   | ③  | 电力按 MW、电价按元/MWh 规定精度填写                                                | 交易平台字段规范                                       |
   | ④  | 电价必须在 **0–540 元/MWh** 区间内，**双侧统一适用**                                  | **课程自定义统一限价**（真实省级限价多在 800–1500 元/MWh，答辩时以此口径说明） |
   | ⑤  | 校验不通过必须给出**具体到 period + 机组 + 段、可读**的错误提示（如 `period34 · G1 段2：申报量为负`）       | 本组工程约定                                         |
   | ⑥  | 每段出力 ≥ 0；段列顺序固定、量价成对出现；允许 0（该时段该段不申报 / 停机）                              | V1.3 新增                                         |
6. **文件约定**：所有数据文件均为 **UTF-8 编码的 CSV**（逗号分隔，第一行为表头，列名与顺序固定，不得增删空列）。Excel/WPS 制作后以「CSV UTF-8 (*.csv)」另存。长表表头：`period,电厂名称,机组编号,第1段出力(MW),第1段报价(元/MWh),第2段出力(MW),第2段报价(元/MWh),…`；段数由表头成对列数决定（最多 5 段 = 10 列）。
7. **时段与颗粒度**：数据以 **96 时段为唯一原生粒度**（每 15 分钟一个，时段 1 = 00:00 起；出处：省间现货规则 4.1 条）。**数据、引擎都只按 96 点跑**；24 仅为展示 / 导出聚合视图（4 点取均值 / 求和），引擎不重算 24。

## 二、发电机组申报表 generator_bids.csv（长表）

**用途**：电厂开市前提交的逐时段"报价单"——每台机组声明"每个时段愿意以什么价格卖多少电"。是供给曲线的来源、出清算法的核心输入。

### 2.1 格式（示意，3 段，96 行以 `…` 截断）

```csv
period,电厂名称,机组编号,第1段出力(MW),第1段报价(元/MWh),第2段出力(MW),第2段报价(元/MWh),第3段出力(MW),第3段报价(元/MWh)
1,金陵电厂,#1机组,120,185,80,255,60,330
1,金陵电厂,#2机组,100,205,70,275,40,350
2,金陵电厂,#1机组,120,185,80,255,60,330
2,金陵电厂,#2机组,100,205,70,275,40,350
…
96,金陵电厂,#1机组,120,185,80,255,60,330
96,金陵电厂,#2机组,100,205,70,275,40,350
```

### 2.2 字段说明

| 列名             | 含义              | 填法与规则                                            |
| -------------- | --------------- | ------------------------------------------------- |
| `period`       | 第几个 15 分钟       | 1–96 连续编号；同一机组在每个时段各一行                            |
| `电厂名称 / 机组编号`  | 机组标识            | 如"金陵电厂 / #1机组"；界面显示用，不得重名                        |
| `第N段出力`        | 该段该时段愿意卖的功率     | MW，一位小数，≥ 0（规则⑥）                                  |
| `第N段报价`        | 该段电的卖价          | 元/MWh，三位小数；0–540 区间（规则④）；低段→高段单调不减（规则②）；缺段留空视为 0 |

- **新能源机组（W/S）不出现在本表**：风电、光伏是价格接受者，实际出力由第五章渗透率 × 形状曲线自动生成，无需申报。
- **无「机组类型」列**：申报表全部为常规机组，撮合与 UI 不再区分燃料类型，供给阶梯图例按机组 / 段价配色；导入旧文件若仍含该列，DataReader 忽略不校验。
- 同一机组同一段跨时段可不同量、不同价 → 模拟**爬坡 / 启停 / 顶峰调峰 / 分时报价**：晚峰出力填大、凌晨填小；平台提供"复制上一时段 / 复制到全部时段"快捷编辑。

### 2.3 逐时段供给

period=t 的供给曲线 = 该周期所有机组各段按报价**升序**堆叠的阶梯，新能源 0 价 RENEW 段优先占位（见第五章）。

## 三、购电申报表 consumer_bids.csv（长表）

**用途**：购电侧（售电公司 / 批发用户，教学简化为聚合申报）的逐时段"询价单"——"每个时段愿意以不高于多少的价格买多少电"。是**需求曲线的唯一来源**（平台只保留**报量报价**一种需求组织方式）。

### 3.1 格式

```csv
period,用户名称,负荷编号,第1段申报量(MW),第1段报价(元/MWh),第2段申报量(MW),第2段报价(元/MWh),第3段申报量(MW),第3段报价(元/MWh)
1,一号工业园区,L1,200,500,150,420,100,350
1,二号商业综合体,L2,250,380,120,300,,,
1,三号居民小区,L3,200,280,,,,
…
96,一号工业园区,L1,180,500,140,420,90,350
96,二号商业综合体,L2,230,380,110,300,,,
96,三号居民小区,L3,210,280,,,,
```

- 列结构与 `generator_bids.csv` 对称：period 行 + 主体 + 段成对列；缺段留空视为 0。

### 3.2 需求形成与校验

1. **需求曲线**：period=t 的需求 = 该周期全部用户段按报价**从高到低**聚合的递减阶梯，与供给阶梯交叉出清——用户自己决定每个时段买多少、出什么价；
2. **一键预填（工具，非撮合输入）**：新建/导入长表时可选"按负荷曲线预填"：
   - 记用户 k 第 s 段的基准申报量 `q_{k,s}`（导入窄表时为其单段数值），预填 `q_{k,s}(t) = q_{k,s} × w(t)`；
   - `w(t) = 负荷(t) ÷ 平均负荷`（均值=1 → 平均申报量不变，与旧口径可比）；
   - 预填只缩放**每段申报量**，**报价默认全时段复制**，预填后**逐格可改**；
3. **平衡校验（保存/导入提示，不阻断）**：
   - 逐时段口径：对每个 t，`Σ用户申报量(t)` 与 `负荷(t)` 的偏差曲线在 P1 显示提示（偏差 = 该时段供需缺口预测）；
   - 总量口径：`ΣΣ 申报量` 与 `Σ 负荷曲线` 总量偏差提示；
   - 只提示讲解用，不强制相等（允许老师刻意做"供不应求/过剩"场景）。

## 四、负荷曲线 load_curve.csv

**用途**：一天 96 个时段、每个时段全社会用电功率。**定位：预测输入（非申报）**，由典型日预设模板（双驼峰形状系数）× 峰值数值自动生成。**不直接进入撮合**，承担四项职责：

| 角色       | 说明                              | 使用方       |
| -------- | ------------------------------- | --------- |
| ① 预填模板   | `w(t)=负荷(t)/平均负荷`，见 §3.2-2     | P1 按钮     |
| ② 平衡校验锚点 | 见 §3.2-3                        | P1 保存校验   |
| ③ 渗透率基准  | `P_re(t)=渗透率×负荷(t)`，见第五章        | B / C 换算  |
| ④ 展示对照   | 电价曲线图叠加"负荷预测"参考线                | C 图表      |

### 4.1 格式

```csv
时段,时刻,负荷(MW)
1,00:15,820.0
2,00:30,790.0
3,00:45,765.0
……（共 96 行，第 96 行对应 24:00）……
96,24:00,700.0
```

### 4.2 字段说明

| 列名   | 含义         | 填法与规则                                          |
| ---- | ---------- | ---------------------------------------------- |
| `时段` | 第几个 15 分钟  | 1–96 连续编号，一行一个，不得缺号、不得重复                       |
| `时刻` | 对应钟点（给人看）  | 00:15 起步、24:00 收尾，每行递增 15 分钟                   |
| `负荷` | 该时段全社会用电功率 | MW，一位小数，大于 0；整体呈双驼峰形态（凌晨低谷、早高峰约 8 点、晚高峰约 19 点） |

> **生成与存储约定**——A 提供的预设模板为 96 点**形状系数**（0–1），界面填峰值（MW）后按 `形状系数 × 峰值` 展开成 96 点负荷曲线。存储只存 96 点基准；24 时段由系统聚合（总则第 7 条），不存在 24 点版本的文件。

## 五、新能源出力 renewable_output.csv 与渗透率

**用途**：风电、光伏机组的**基准出力形状**（分时段）。实际出力不直接用表中的值，而是由 P2 的**渗透率滑块（0–100%，默认 20%）**统一换算。

### 5.1 格式

```csv
机组ID,机组类型,时段,出力(MW)
W1,风电,1,35.0
W1,风电,2,38.0
……（W1 共 96 行）……
S1,光伏,1,0.0
S1,光伏,2,0.0
……（夜间光伏全为 0，白天逐时段变化）……
S1,光伏,50,52.0
```

### 5.2 字段说明

| 列名              | 含义             | 填法与规则                                                 |
| --------------- | -------------- | ----------------------------------------------------- |
| `机组ID / 机组类型`   | 哪台新能源机组        | 如 W1、S1；类型只能填 风电 或 光伏；**新能源机组只存在于本文件**，不出现在 generator_bids |
| `时段`            | 第几个 15 分钟      | 1–96；**每台机组各占 96 行**                                  |
| `出力`            | 该时段的**基准形状**出力 | MW，一位小数；≥ 0；光伏夜间为 0、午间（约 11–14 点）最大；风电整夜有波动           |

### 5.3 渗透率换算公式（B、C 必须用同一式）

**定义：渗透率 = 新能源出力 ÷ 负荷（瞬时出力占比）**。滑块变动时按下列步骤换算，保留风光各自的形状特征：

1. 该时段风光基准总出力 `P_base(t) = Σ 表中各机组出力(t)`；
2. 该时段新能源实际总出力 `P_re(t) = 渗透率 × 负荷(t)`；
3. 各机组实际出力 `(t) = 表中该机组出力(t) ÷ P_base(t) × P_re(t)`（该时段 `P_base(t) = 0` 时，各机组出力均为 0）。

B 的算法与 C 的界面（曲线预览）都必须按此式计算——**两边算出的数必须一致**，否则联调时对不上。

- **为何参照负荷(t) 而非申报量(t)**（2026-09-02 确认）：① 行业口径——渗透率 = 新能源发电量 / 全社会用电量（负荷）；② 职责分离——申报量是学生可编辑的决策变量，若锚在申报量上，改一格购电申报会导致新能源出力连动，两个旋钮互相干扰；③ 预填平衡态下 Σ购电申报(t) ≈ 负荷(t)，两口径数值几乎一致；④ 刻意失衡场景中新能源应随负荷（场景）出力，供需缺口由申报单独体现。极端时段申报需求 < P_re(t) 时，0 价 RENEW 先成交、多余部分不成交（隐含弃风弃光，可作进阶讨论）。
- **渗透率上限**：滑条 0–100%，默认 20%；高占比（>80%）不对应现实运行场景，仅供观察"全绿 → 电价归零、常规机组挤出"的极限演示，日常演示建议 20–60%。
- 新能源以同一 **0 价 RENEW 供给段**进入撮合（价格接受者、优先占位），引擎处理路径与旧版一致。

## 六、仿真模式与对拍

**平台只保留一种需求组织方式：报量报价（双侧长表）。** 控制维度收敛为：

| 维度（P2 设置） | 取值            | 影响                                  |
| ---------- | ------------- | ----------------------------------- |
| 定价结算模式    | MCP / PAB     | 结算口径，不影响出清价格的形成                     |
| 显示粒度      | 96 / 24       | **引擎只跑 96**；24 为聚合视图（见第七章 7.2）     |

**所需文件**：generator_bids + consumer_bids + load_curve + renewable_output（报量报价单模式，四表齐备）。

**基准对拍（验收锚点）**：
- 旧窄表基准例文件**不改格式**，导入后复制为 96 行同量同价，新引擎逐时段结果应与旧引擎恒量结果**完全一致**——窄表等价性对拍；
- 模式一（刚性需求）基准及其对拍口径**取消**；
- 场景数据随 #67 重标定（现样例发电合计 590 MW、购电合计 650 MW，盖不住负荷曲线 688–1136 MW；重标定目标：双侧申报覆盖典型日负荷，默认预填状态下逐时段基本平衡，可演示早/晚峰涨价与新能源压价）。

## 七、出清结果接口（B 生产 · C 消费的对齐边界）

> 前六章约定**输入**，本章约定**输出**——C 的界面只消费本章结构，B 的真实引擎必须按本章结构产出。**结构冻结后 B、C 各自独立开发，联调时零改动对接。**

### 7.1 三个结构（C 已按此实现，见 `ClearingSim/core/fake_engine.h`）

**① `EntityCleared`——单个主体在某时段的成交明细（三视角过滤的核心数据源）**

| 字段          | 类型        | 含义                     |
| ----------- | --------- | ---------------------- |
| `id`        | QString   | 主体 ID（机组 G1 / 用户 U1）   |
| `name`      | QString   | 主体名称（金陵电厂 / 一号工业园区）    |
| `segment`   | int       | 申报段号                   |
| `bidPrice`  | double    | 该段申报价（元/MWh）           |
| `clearedMW` | double    | 中标电量（MWh）              |
| `money`     | double    | 发电侧=收入、购电侧=费用（元）       |

**② `PeriodResult`——单时段出清结果**

| 字段              | 类型                     | 含义                     |
| --------------- | ---------------------- | ---------------------- |
| `period`        | int                    | 时段号                    |
| `time`          | QString                | 时段标签（"01:00" / "00:15"；基准例为"全日"） |
| `loadMW`        | double                 | 该时段负荷                  |
| `renewMW`       | double                 | 该时段新能源出力（优先中标）         |
| `clearingPrice` | double                 | 该时段出清价                 |
| `clearedMW`     | double                 | 该时段总成交电量               |
| `genFee`        | double                 | 发电侧结算总额                |
| `conFee`        | double                 | 购电侧结算总额                |
| `genDetails`    | `QVector<EntityCleared>` | 发电侧逐主体明细             |
| `conDetails`    | `QVector<EntityCleared>` | 购电侧逐主体明细             |

**③ `ClearingResult`——一次完整仿真的结果**

| 字段           | 类型                    | 含义                     |
| ------------ | --------------------- | ---------------------- |
| `mode`       | QString              | `"MCP"` / `"PAB"`      |
| `sourceName` | QString              | 数据源描述                  |
| `periods`    | `QVector<PeriodResult>` | 逐时段结果（基准例 1 个；连续仿真 96 个） |

### 7.2 24 视图聚合（C 展示层，B 不产出）

- `clearingPrice`：每 4 个相邻时段**算术平均**（仅视图，不代表"小时出清价"）；
- `clearedMW / genFee / conFee`：每 4 点**求和**；
- 明细（genDetails/conDetails）不聚合。

### 7.3 B 位对接约定

1. **接口形态**：`FakeEngine` 提供两个静态入口 `clearBenchmark(market, mode)` 与 `clearPeriods(scenarios, market, mode)`（详见 `core/fake_engine.h`）。V1.3 引擎的 `clearPeriods` 改为**逐 period 取长表 period=t 行 + 渗透率出力**撮合，签名变化属 #67 实施细节，另行登记；结构体不变，C 的界面与三视角过滤零改动。
2. **MCP 口径**：全场统一按边际段报价 `clearingPrice` 结算；`genDetails`/`conDetails` 的 `money = clearingPrice × clearedMW`。
3. **PAB 口径**：各段按自身报价结算；`money = bidPrice × clearedMW`；出清价本身不受影响。
4. **对拍锚点**：窄表基准例导入展开后逐时段结果与旧引擎一致（见第六章）。
